# T-218: task-card request ownership

Selecting another task while detail or action requests were pending could let an
older response overwrite the new card. Fetch/JSON failures could leave loading
visible, and repeated clicks could send concurrent task commands.

Each detail load now creates a distinct task context. Detail, action and report
refresh continuations check that context after asynchronous boundaries before
changing the visible card, selected detail, cache or closure-policy preview.
Loading clears the previous detail so a language rerender cannot resurrect it.

Task commands and closure-policy requests share one pending action per context.
They disable their controls, preserve existing disabled states across rerenders,
display safe current errors, and restore controls for a retry. Navigation creates
an independent context; a late action neither paints it nor refreshes the old task.
Existing confirmation phrases, token headers and backend action payloads remain.
This client guard does not establish backend exactly-once execution.

Deterministic node:vm tests run the actual browser fragments with deferred fetch
and JSON bodies. Native expected-red evidence precedes the implementation.
Validation also covers the affected dashboard/task server suite and a real Linux
Chromium request-ordering and repeated-action check; no Windows coverage is claimed.
