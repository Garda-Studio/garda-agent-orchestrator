# Native source acceptance after local commit

After a successful native post-commit hook, `human-commit` runs the genuine
task audit and checks the published commit, accepted tree and original parent.
It then exclusively creates a task/commit-specific snapshot under
`runtime/reviews/<task-id>-source-acceptance-<commit>.json` and publishes the reserved
`TASK_SOURCE_COMMIT_ACCEPTED` event. The event binds the workspace, Git IDs,
snapshot path and SHA256. The snapshot contains the actual post-commit audit
and its JSON SHA256, authenticated with the existing workspace-local commit
audit API. No permission key is created or rotated by this producer.

Snapshot bytes are bounded to 8 MiB and flushed through their retained ordinary
file descriptor. Before canonical event append, captured containing directories
are opened without blocking, checked against their ordinary-directory identities
and flushed from the snapshot namespace up to the project root. This also
persists newly created namespace entries. The transaction then rechecks snapshot
bytes, path identity, Git identity and workspace authority. Directory acquisition
or synchronization errors, including unsupported filesystem durability barriers,
withhold acceptance; no best-effort directory sync substitutes for this proof.
Changed identity/content, uncertain audit, revoked authority or failed hooks also
block publication. Real commits and diagnostic snapshots remain preserved.

Later commits never overwrite earlier proof. Consumers must verify the native
event, workspace authentication, immutable bytes and source composition; a
snapshot alone is not acceptance. Key rotation can make an old binding
unverifiable and must remain blocking. No new binding is assigned to an old
child commit or historical suite run, and this producer does not resolve
aggregate parent audit, memory or original validation obligations.

## Windows integration

Directory handles use `O_RDWR` on Windows because `FlushFileBuffers` requires
write access; POSIX retains `O_RDONLY`. Every captured containing directory is
still synchronously flushed deepest-first before canonical publication. An
access-denied, I/O, unsupported-barrier or identity error withholds acceptance
while preserving the real commit and diagnostic snapshot.

Windows namespace durability is supported only for a verified local fixed NTFS
volume. The bounded existing PowerShell/.NET inspector must return ready NTFS
for the captured drive; unknown, remote, non-NTFS, malformed, unavailable or
timed-out inspection is blocking. The volume-to-snapshot path is independently
captured, rejects junctions and cross-device paths, and is rechecked around
each barrier. A successful flush alone does not establish support on other
Windows filesystems. The implementation adds no best-effort fallback or new
flush backend.

The inspector uses the OS-owned `GLOBALROOT/SystemRoot` PowerShell executable,
system working directory and minimal environment. Strictly typed `DriveInfo`
predicates validate the capability before `Console.Out.Write` emits a fixed
report; no command or module lookup serializes it. Caller PATH, SystemRoot and
user module-search entries cannot supply a capability report. Reauthentication
starts from unsigned proof content and requires a newly returned matching
workspace binding and HMAC. Missing key/context cannot reuse the old signature
or create a replacement permission key.

The local regression uses real file and directory flushes and checks all
containing directories, snapshot-before-directory order and Windows write
access. Negative coverage retains real commits while rejecting `EPERM`,
`EIO`, `EINVAL`, unsupported volumes and changed proof bytes or identities.
These checks do not represent a physical power-loss test.
