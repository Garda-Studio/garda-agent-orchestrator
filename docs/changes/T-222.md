# Trusted snapshot rollback destinations

Snapshot rollback now admits exact destination units from the trusted update and
uninstall producers before either preview or safety-snapshot creation. Editing
snapshot records and recomputing their integrity hashes cannot authorize another
hook, an unrelated source file, or an alias of a supported path. Missing-file
records receive the same check as records that contain replacement bytes.

Existing producer-supported historical record sets and the legitimate pre-commit
hook remain supported. The default init-answers destination remains valid; a
custom historical init-answers destination requires the matching trusted
`--init-answers-path` input (or the API option). Snapshot-local metadata and its
reported version cannot supply that permission. Record selection is checked
again immediately before restore, and a changed selection triggers the existing
safety rollback rather than applying a stale selection.

Failure recovery in snapshot and version modes retains the originally captured
safety record selection. Before restoring it, the reread records must pass the
same trusted destination admission and match that captured selection. A changed
safety selection fails closed, preserving its evidence and reporting both the
original failure and the safety-recovery failure without applying the changed
selection. This does not promise restoration when the safety snapshot was altered.

This is a destination admission boundary, not authentication of payload origin
within an already authorized recovery unit. Existing physical containment,
snapshot-integrity, lifecycle-lock and linked-worktree controls remain active.
No snapshot-format migration or new signing authority is introduced.

The owning rollback and CLI suites cover recomputed-integrity attacks, preview
rejection, custom answers, supported historical paths and selection changes,
including forged hooks, unrelated deletion records and changed supported
selections in both modes' safety snapshots.
The existing common snapshot suite covers lower-level integrity compatibility.
Validation in this owner checkout runs on Linux; Windows integration acceptance
must be established separately by the coordinator.
