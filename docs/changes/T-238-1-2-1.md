# Disputed lock ownership conflicts

Timeline and lifecycle claimed-directory mismatches refuse canonical publication
and report an explicit conflict. The accepted bounded preservation helper may
retain a verified external copy; the disputed original and any partial capture
remain in place. Copies provide custody without restoration or deletion authority.

Timeline callers may supply an explicit project root through in-process options
and acquired handles. It is not inferred from cwd, lock paths or owner metadata.
Lifecycle uses its existing normalized target. Missing roots and unsupported
storage ownership proof refuse copying. Async lifecycle conflicts still remove
their local queue entry so subsequent operations can proceed.

An owner replaced before the existing claim may already have moved into the
disputed claimed path. Preserve that physical directory and exact owner bytes;
canonical path stability in that window is not promised. A separate canonical
owner appearing after the claim is preserved independently. This introduces no
atomic source-claim promise, new backend, toolchain or architecture.

Current regressions require explicit conflicts and compare dev, ino, mode,
birthtime, uid, gid and exact owner bytes, retaining existing lock-id and operation
assertions. The timeline owning tests replace their incompatible historical
republish expectation. Queue progress is checked after an async release conflict.

Validation uses the owning lifecycle, timeline, preservation-helper and task-queue
transaction suites. Windows cannot verify owner-managed copy storage through the
existing POSIX ownership contract and must retain the original while refusing
that copy. Actual platform outcomes are recorded with the task's native evidence;
historical Linux results do not establish current Linux or macOS acceptance.
Separate real native owner schedules in T-238-1-2-2 and parent acceptance remain
independent obligations.
