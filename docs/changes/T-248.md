# Authenticated protected task continuation

Initial protected entry and any scope, permission, provider, intent or configuration change still require fresh explicit operator approval.
An explicit upgrade or ordinary native repeat entry of the same active task may omit confirmation flags only when its exact scope and permission flags remain unchanged.
The native entry stores a domain-separated HMAC record in workspace-private Git metadata. It binds the physical checkout and Git directory,
the exact entry artifact, latest entry event and current configuration. Runtime files, copied receipts or edited artifacts cannot create authority.
Continuation retains the original operator-confirmation timestamp. It does not refresh consent, authorize another task or waive current gates.
Missing, modified, linked, foreign or revoked records fail closed; terminal/reset history or a changed task requires a new admission.
Legacy entries without this authenticated record retain the existing fresh-confirmation behavior. The generic ten-minute validator is unchanged.
Each successful admission rotates its task-private key before publishing the new record. Replaying an older signed record fails;
interruption between those writes leaves the old authority revoked. Other tasks use separate keys.
The protected receiver uses resolved canonical provider and route identities, so supported aliases retain the same permission boundary.
Synchronous and asynchronous native terminal event append revoke the private task key before canonical publication;
restoring earlier public task-mode and timeline files cannot undo that revocation. Failed revocation blocks the append.
Duplicate or rejected conditional appends do not revoke an unchanged grant. Diagnostic reset-refusal events are not terminal events.
The native reset/discard writer also revokes admission before deleting task history or artifacts, since reset does not publish a terminal event.
Admission publication, terminal event publication and destructive reset share the canonical task-event lock.
Publication rechecks the key and native entry under that lock; reset retains it through artifact deletion and queue status synchronization.
The reset releases the task lock before aggregate-log maintenance, preserving the existing lock order.
Preparation, preview and refused reset leave admission standing. Failed private revocation prevents destructive reset effects.
The protected guard accepts only a process-local verified proof bound to its exact requested scope; serialized flags or grant records are insufficient.
A technical validation failure does not revoke unchanged permission. Failed authority publication invalidates task-mode evidence before returning failure.

Regression coverage exercises elapsed-time continuation, expanded scope, changed provider/intent, explicit refusal, tampering, missing authority,
terminal status, actual reset/discard with public-state rollback, failed reset revocation and copying a grant between native checkouts.
Every completion still requires current tests, independent review and audit.
