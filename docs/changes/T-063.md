# Guarded selected backup deletion

`previewBackupDeletion({ targetRoot, snapshotIds })` reads the existing rollback
snapshot inventory and returns the exact selected IDs, sizes, recovery health,
lost and remaining recovery points, a final-point warning and a confirmation
token. It creates no preview receipt, lock or mutation generation.

`deleteSelectedBackups` additionally requires `confirm: true` and the exact
`confirmationToken`. When the preview warns about the final recovery point or
last backup, `confirmFinalRecoveryPoint: true` is also required. The token binds
the selection, canonical target and ancestry, snapshot membership, creation and
stat identities, and captured bytes. It is a freshness binding, not a secret or
a replacement for caller authorization.

Both operations accept dense unique inventory IDs, never snapshot paths.
Inspection rejects links, hard links, mount and nested repository boundaries,
missing or replaced snapshots, and bounded-inventory overflow. Snapshot health
is reconstructed from retained bounded bytes using the existing rollback record
and integrity format; it never follows a second live read into an escaped tree.
Corrupt snapshots remain explicitly diagnosed and can be selected for deletion
while healthy unselected recovery points are preserved.

Confirmed deletion owns the existing lifecycle lock and runtime mutation
generation. Direct creation and retention also acquire that lifecycle lock;
existing caller-held create/retention locks remain reentrant. Selected deletion
rejects an already-held lifecycle lock, including same-process restore/create.
Before each selected snapshot it reconstructs the remaining inventory. Removal
uses retained member bindings and individual nonrecursive operations. Successful
unlink bytes and fully removed IDs are separate. A failure stops the batch,
preserves unattempted selections, and reports any inventory-refresh failure.

## CLI

```text
garda backup delete --snapshot-id ID --snapshot-id OTHER_ID --dry-run --json
garda backup delete --snapshot-id ID --snapshot-id OTHER_ID --confirm --preview-token HASH --json
```

Add `--confirm-final-recovery-point` only after acknowledging the preview warning.
Preview and confirmation flags cannot be combined. Partial failures return a
non-zero CLI exit with the retained result and actual removal counters.

## UI handoff

The UI owner supplies its server-configured `targetRoot`, explicit IDs and the
returned token through its existing authorized confirmation boundary. The backend
owns the lifecycle lock: do not wrap selected deletion in another held lifecycle
lock. Display the warning and obtain the separate final-point confirmation;
handle `result: ERRORS` and `inventoryRefreshed: false` without claiming deletion
or refresh succeeded. No UI implementation is included here.

Inventory limits are 128 selected IDs, 2,048 directory entries, 100,000 captured
members, 64 MiB per file, 1 MiB per records/integrity/display metadata file and
2 GiB total inspected payload. Exceeding a bound preserves all snapshots.

Backend and CLI regression coverage includes selection/token replay, replaced
physical identities, corrupt health, unsafe containment, real process lock
contention, final-point confirmation and truthful partial permission failures.
Validation is source-qualified; Windows, WSL and browser coverage must be supplied
by the receiving owner rather than inferred from Linux tests.
