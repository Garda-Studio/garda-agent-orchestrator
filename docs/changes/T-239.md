# T-239: Heartbeat ownership across replacement

Timeline and lifecycle heartbeats validate owner metadata and persist the update
through the same open descriptor. They open only an existing ordinary, singly
linked owner file without truncation or creation, then compare its device,
inode, mode and birth time against the observed object. A replaced file opened
after observation, symlink, hard-link alias or unknown inode is skipped. Existing
metadata parsers still normalize the same fields and require the expected lock
ID before producing a heartbeat payload.

Writes start explicitly at position zero, handle partial writes and truncate any
remaining suffix on that descriptor. The descriptor is always closed. Replacing
the canonical lock directory after validation cannot redirect this write into
the replacement owner's file. Ownership changes continue to create a new file
object; heartbeat does not provide compare-and-swap for another writer that
changes a lock ID in place on the same inode. The canonical directory plus
`owner.json` layout, metadata schemas, public readers and reclaim policy remain
unchanged. Missing or invalid owners are not recreated or overwritten; other
I/O failures retain the heartbeat warning path.

Before the implementation, two native expected-red runs at source HEAD
`14528fef5c41cdf5bceab51bbb700fda7699f2b1` confirmed replacement overwrite in
each writer. A separate process renamed the old directory and acquired a real
new lock through the existing API. Regression checks preserve the new inode and
exact bytes through the old heartbeat and release, then reclaim the deliberately
exited replacement owner. Additional checks cover live heartbeat identity,
short writes, suffix truncation, failed-write descriptor closure and malformed,
missing, foreign or aliased metadata. Actual execution is Linux; Windows
execution is not established by this change's local checks.

The separate T-238 directory restoration goal and its saved prototype remain
incomplete. This change does not add a directory no-replace backend or alter its
native WIP routing.
