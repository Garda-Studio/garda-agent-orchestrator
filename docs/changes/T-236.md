# T-236: Bound automatic aggregate-journal retention work

Large JSONL records exceed the 512-byte-per-line size heuristic even at the
configured retained-line limit. Previously each append counted the entire journal
and rewrote it back to that limit; repeated retention checks also rescanned an
unchanged file. The existing LF append separator was already correct.

Automatic retention now keeps an advisory count for at most 64 absolute paths.
It trusts a count only for an ordinary, single-link file with matching device,
inode, birth time, mode, size, modification time, change time and retention cap.
The existing aggregate lock covers inspection, append, count advancement and
pruning. File replacement, a same-size rewrite or a changed cap triggers a fresh
streamed count. Unknown identity uses the existing full-prune path. An
unterminated tail is never cached. Failed replacement retains the actual count
and retries retention on subsequent writes.

When the cap is exceeded, automatic pruning targets the cap minus
`min(100, floor(cap / 100))` lines. This preserves the configured upper cap and
newest-record order while removing at most 1%/100 additional oldest records per
prune. Caps below 100 keep their exact target. Explicit pruning, protected-task
exceptions, lock ownership, atomic replacement and public schemas are unchanged.
This cache is an optimization, not durable evidence or authority.

Seven new owning regressions cover sync/async rewrite work, unchanged-file scan
work, same-size rewrites, physical replacement, a reduced cap and failed-prune
retry. The native test-first run failed exactly four new work-budget assertions
before implementation; focused candidate validation then passed. Final affected
validation also includes the existing append and lock suites.

One real Linux/Node v24.19.0 process ran the same probe for 64 operations per case:

| Retained cap / payload | Operation | Aggregate bytes read, before / after | Replacements, before / after |
| --- | --- | --- | --- |
| 256 / 1024 bytes | sync or async append | 39,348,572 / 7,700,224 | 64 / 22 |
| 2048 / 4096 bytes | sync or async append | 1,090,651,548 / 42,626,382 | 64 / 4 |
| 256 / 1024 bytes | sync or async unchanged-file apply | 17,540,224 / 274,066 | 0 / 0 |
| 2048 / 4096 bytes | sync or async unchanged-file apply | 543,091,328 / 8,485,802 | 0 / 0 |

The 2048-line sync append case took 964.51 ms before and 74.34 ms after; this is
a single bounded sample, not a whole-CLI latency guarantee. Append cases verified
the upper cap and all 64 newest records in order; unchanged-file cases preserved
all original records. Measurements used the baseline published retention module
and the freshly compiled candidate validation module respectively. Exact probe,
source/module hashes and complete results are retained in the task-owned
`runtime/manual-validation/T-236/performance-{baseline,candidate}.json` and logs.
Windows, cross-process cache reuse and unrelated timeline/SQLite latency are not
claimed. Existing concurrent-writer tests remain part of affected validation.
