# Quality checklist template persistence

The checklist owner retains effective policy, answer assessment and reusable
answer validation. A dedicated template persistence module owns contained file
reads, authenticated sidecar bindings, native task-event evidence and repair
materialization. The shared template contract holds the unchanged schemas and
canonical fingerprint comparisons. Imports flow from the checklist owner to
persistence and the contract; persistence receives the existing policy functions
and does not import the checklist owner or its barrel.

Existing public exports, serialized fields, event sources, binding hashes and
repair result statuses remain compatible. Filled answers are reused only under
the existing task, preflight, policy fingerprint and authenticated event checks.
Unsafe originals and repair candidates remain preserved; warnings remain bounded.

Template and binding files use the existing core atomic writer. Each replacement
is atomic independently, with the existing order of template, binding and native
event publication. This is not a transaction across all three artifacts. A failed
replacement leaves its previous complete file and publishes no binding event;
later stale reuse still requires a matching authenticated binding.

Focused regressions cover failure at each file publication boundary and missing
binding event evidence, alongside existing stale, tampered, foreign-path,
symlink and reusable-repair cases. A genuine native test-only phase against the
accepted source produced two atomic publication assertion failures with 57
passing controls, including the missing-event regression. Native task acceptance
also requires the
affected consumer suites and fresh code, refactor, API, security and test reviews.
Linux is the executing platform; Windows and macOS filesystem execution remains
unverified.
